Asset Interventions

The com.zepben.commons.hc.intervention package provides the common model for candidate-driven asset interventions used by hosting capacity workflows. An asset intervention is a planned CIM network change, such as installing a BESS, adding an OLTC control, moving a tap, or upgrading a line or transformer.

The package separates intervention processing into three stages:

  1. InterventionCandidate: a ranked opportunity to make an intervention.
  2. DatedInterventionAllocation: a concrete intervention selected for a specific year.
  3. AppliedInterventionDetails: an audit payload returned after the allocation mutates a NetworkService.

Candidates​

An InterventionCandidate identifies a possible intervention and carries the scheduling fields common to all candidate types:

FieldPurpose
rankCandidate priority. Lower values are processed first.
yearStart / yearEndInclusive year range in which the candidate may be allocated.
feederIdFeeder the candidate applies to.
weightAmount of yearly allocation budget consumed by the candidate.

Concrete candidate classes add intervention-specific data. For example, a BESS candidate has a target conducting equipment mRID and required capacity, while a thermal line upgrade candidate has target original line mRIDs and a required current rating.

Candidates are usually loaded from the input database with InputFetcher.fetchInterventionCandidates. That method reads intervention_candidates for a work package and InterventionClass, optionally filtered by feeder and scenario, then decodes the row into the matching candidate class. It is the live-database entry point used when a model generator needs to turn saved candidate rows into Commons intervention objects.

Allocations​

Each concrete intervention processor extends AssetInterventionProcessor. The common identifyAllocations method:

  1. Iterates over configured allocation years.
  2. Selects candidates whose active year range contains the current year.
  3. Sorts those candidates by rank.
  4. Adds candidates until InterventionAllocationCriteria.limitPerYear is exceeded.
  5. Removes selected candidates so they are not considered again for later years.
  6. Applies the feeder filter after yearly selection, so yearly limits are consistent across feeders in the same scenario.
  7. Calls the concrete processor's allocationForCandidate to convert each local candidate into an InterventionAllocation.

The result is a list of DatedInterventionAllocation objects. Each one contains the year, the allocation to apply, the original candidate, and the selected instance name where an instance catalogue was involved.

AssetInterventionInstance objects are catalogue entries or preset configurations used by some processors while allocating. Examples include BESS model settings, LV STATCOM settings, conductor catalogue entries, transformer catalogue entries, and OLTC control settings. Some intervention classes, such as distribution tap optimization, do not need instances.

Application​

InterventionAllocation represents the actual CIM mutation. It can be applied to either:

MethodNetwork shape
applyToA simplified network, using an original-to-simplified object map to resolve collapsed objects.
applyToUnsimplifiedAn unsimplified network. By default this delegates to applyTo with an empty mapping.

When an allocation is applied it mutates the NetworkService and returns an AppliedInterventionDetails subtype. Those details contain the data needed by a caller to record what was applied, for example in applied intervention result tables. Commons defines the details objects and returns them from allocations; the caller decides whether and where to persist them.

One common orchestration pattern is:

  1. Fetch all candidates for the intervention class, work package, and scenario with fetchInterventionCandidates.
  2. Fetch or construct allocation criteria for the intervention class.
  3. Fetch intervention instances when that class uses a catalogue.
  4. Dispatch to the matching AssetInterventionProcessor.identifyAllocations.
  5. During model generation, apply allocations whose DatedInterventionAllocation.year matches the model year.
  6. Keep the returned AppliedInterventionDetails with the dated allocation as the audit record for that applied change.

Example​

This example shows a thermal transformer upgrade going from a candidate to a dated allocation, then to applied intervention details. In a production workflow the candidate and transformer catalogue instance would commonly come from InputFetcher.fetchInterventionCandidates and InputFetcher.fetchInterventionInstances; here they are constructed directly.

import ch.qos.logback.classic.LoggerContext
import com.zepben.commons.hc.intervention.ThermalTransformerUpgradeInterventionProcessor
import com.zepben.commons.hc.intervention.allocation.AppliedTransformerUpgradeDetails
import com.zepben.commons.hc.intervention.allocationCriteria.ThermalTransformerUpgradeAllocationCriteria
import com.zepben.commons.hc.intervention.instance.TransformerCatalogInstance
import com.zepben.commons.hc.intervention.interventionCandidate.ThermalTransformerUpgradeCandidate
import com.zepben.commons.hc.logging.HCLogger
import com.zepben.ewb.cim.iec61968.infiec61968.infassetinfo.TransformerConstructionKind
import com.zepben.ewb.cim.iec61968.infiec61968.infassetinfo.TransformerFunctionKind
import com.zepben.ewb.cim.iec61970.base.wires.PowerTransformer
import com.zepben.ewb.cim.iec61970.base.wires.PowerTransformerEnd
import com.zepben.ewb.services.network.NetworkService
import org.slf4j.LoggerFactory

val network = NetworkService()
network.add(
    PowerTransformer("tx-1").apply {
        constructionKind = TransformerConstructionKind.overhead
        function = TransformerFunctionKind.distributionTransformer
        addEnd(PowerTransformerEnd("tx-1-e1").apply {
            endNumber = 1
            ratedU = 11_000
            r = 1.8
            x = 2.4
        })
        addEnd(PowerTransformerEnd("tx-1-e2").apply {
            endNumber = 2
            ratedU = 415
        })
    }
)

val candidate = ThermalTransformerUpgradeCandidate(
    powerTransformerId = "tx-1",
    requiredKva = 250.0,
    rank = 1,
    yearStart = 2026,
    yearEnd = 2026,
    feederId = "fdr-1"
)

val catalogueEntry = TransformerCatalogInstance(
    id = "500-kva-overhead",
    description = "500 kVA overhead distribution transformer",
    ratedKva = 500.0,
    primaryVoltageLevel = "MV",
    applicablePrimaryBaseVoltages = listOf(11_000),
    secondaryVoltageLevel = "LV",
    applicableSecondaryBaseVoltages = listOf(415),
    supportsPrimaryPhaseCode = "XYZ",
    supportsSecondaryPhaseCode = "XYZN",
    constructionKind = "overhead",
    functionKind = "distributionTransformer",
    r = 1.2,
    x = 2.0
)

val logger = HCLogger((LoggerFactory.getILoggerFactory() as LoggerContext).getLogger("interventions"))
val datedAllocation = ThermalTransformerUpgradeInterventionProcessor.identifyAllocations(
    feederId = "fdr-1",
    networkService = network,
    candidates = listOf(candidate),
    allocationCriteria = ThermalTransformerUpgradeAllocationCriteria(
        limitPerYear = 1.0,
        years = listOf(2026)
    ),
    instances = listOf(catalogueEntry),
    logger = logger
).single()

val details = datedAllocation.allocation.applyToUnsimplified(network) as AppliedTransformerUpgradeDetails

println(datedAllocation.year)          // 2026
println(datedAllocation.instanceName)  // 500-kva-overhead
println(details.ratedKva)              // 500.0
println(details.r)                     // 1.2
println(details.x)                     // 2.0

Implemented Asset Interventions​

Intervention classProcessorDescription
COMMUNITY_BESSBessInterventionProcessorSelects a BESS instance for a measurement-zone candidate, finds a suitable connectivity node, adds or reuses a PowerElectronicsConnection, and installs a BatteryUnit with control metadata.
DISTRIBUTION_TX_OLTCDistributionTransformerOLTCInterventionProcessorAdds or enables OLTC control on a distribution transformer primary end, using configured tap changer control settings.
DISTRIBUTION_TAP_OPTIMIZATIONDistributionTapOptimizationInterventionProcessorChanges a distribution transformer tap changer normalStep by a candidate-provided delta, clamped to the tap changer's configured bounds.
LV_STATCOMSLvStatComInterventionProcessorSelects an LV STATCOM instance, finds a suitable LV connectivity node by distance and X/R ratio, and installs a StaticVarCompensator.
THERMAL_LINE_UPGRADEThermalLineUpgradeInterventionProcessorSelects the smallest compatible conductor catalogue entry that satisfies required current, voltage, phase, wire class, and non-increasing impedance checks, then applies it to the target original line or lines.
VOLTAGE_LINE_UPGRADEVoltageLineUpgradeInterventionProcessorApplies a candidate-recommended conductor catalogue entry to the target original line or lines.
THERMAL_TRANSFORMER_UPGRADEThermalTransformerUpgradeInterventionProcessorSelects the smallest compatible transformer catalogue entry by rating, voltages, phases, function, and preferably construction kind, then updates transformer ratings and primary impedance values.

InterventionClass also contains values such as load reshaping, DVMS, and phase rebalancing. Those are not implemented as asset intervention processors in this package.
